## 二、还原出的功能规格

**DEX 重新划分**

1. 两种互斥模式（标签「分配方式」）：
   - **均匀分配**：输入「生成的Dex数量」，尽可能均匀地把代码分配到每个 dex。
   - **按限制分配**：输入「方法数量限制」，限制每个 dex 中的**方法数**；最大 65536，推荐 64000。
2. 单个 dex 方法数硬上限 **65536**，超出**明确报错**，不静默产出。
3. 均匀分配时数量太小装不下 → **弹确认框询问「是否自动增加 dex 数量」**，用户确认后才自动增加；未经确认不产出。
4. 生成多个 dex 时警告 Android 5.0 以下系统无法运行。
5. 进度文案「正在重新分配…」。

**DEX 混淆对抗**

1. 由「自定义匹配规则」（正则，一行一条）驱动重命名字段名 / 方法名 / 类名 / 包名。
2. 子类类名先按 `$` 分割再逐段匹配（`Name$a` → `Name`、`a`）。
3. 包名按 `/` 分割逐段匹配，最后尝试整体匹配；`.*` / `.**` 分别对应「不含子包 / 含子包」。
4. 重命名结果必须能生成合法 dex（`classes3.dex` 的 65536 校验同样适用于改写后的 dex）。

## 三、与 Cyber-Hub-Manager r15 的偏差及本轮修改

| # | 偏差 | MT 依据 | 本轮修改 |
|---|---|---|---|
| 1 | 「指定 DEX 数量」模式下 `maxClasses` 默认 1，导致 19379 个类各拆一个 DEX，**静默产出 40MB 坏 APK** | `0x7f120293` / `0x7f120292` | `maxClasses` 默认 0；`count` 与 `methodLimit` / `maxClasses` 互斥 |
| 2 | 第二种模式是「按每个 DEX 的类数」，与 MT 不符 | `0x7f120296/297/298` | 改为「按限制分配 · 方法数量限制」，默认 64000、上限 65536 |
| 3 | 无 65536 方法数硬约束，超限时静默多切 DEX | `0x7f12028a` + `classes3.dex` smali | 加 `DEX_METHOD_LIMIT=65536`，单类 / 单组超限明确报错 |
| 4 | 数量太小装不下时静默产出更多 DEX | `0x7f120292` | 后端抛 `NEED_MORE_DEX:n:65536`，前端 `confirmBox` 询问后带 `autoIncrease=true` 重跑 |
| 5 | 对话框文案与 MT 不一致 | `0x7f120291/293/294/296/297/298/299/29a/29b` | 前端全量对齐；进度「正在重新分配…」r15 已对齐 |
| 6 | 混淆对抗重命名去重失效，多个类映射成同名导致 `already been interned` 崩溃 | `0x7f120263` + dex 合法性约束 | 去分号去重 + `reservedTypes` 保留集合；`containsObfName` 按 MT 的 `$` 分割逐段匹配 |
