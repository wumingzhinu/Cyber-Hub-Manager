需求与现状差距

用户要求「所有处理加上处理进度」，并给出 MT 管理器截图：Dex转Jar 标题 + 处理中... + 蓝色进度条。

r13 及之前只有两种反馈：

  • 顶部一条 2px 的 #progress 忙条（body.busy 触发），只是「在转」，没有标题、没有阶段、没有百分比；
  • APKS 转换的 bundleProgress(job,message) 只更新一段文字，没有进度条。

DEX 转 JAR 这类操作可能持续数十秒，用户只能盯着界面猜「是不是卡住了」。本轮把进度提升为一等公民。

半透明遮罩、居中圆角卡片、大号标题、灰色说明、6px 轨道 + 蓝色填充；本实现完全按此还原，深浅主题自适应。

方案：三层结构

层实现作用
界面层app.html 新增 #taskProgress（tpTitle / tpMsg / tpTrack / tpFill）；style.css 新增 .taskProgress / .tpCard / .tpFill / @keyframes tpIndetMT 同款卡片；hidden 默认隐藏，indeterminate 走不确定动画
调度层app.js 的 rpc() 按 action 查 TASK_TITLES，命中即 taskProgressOpen(title) 并注入 __task；成功 / 失败回调都 taskProgressClose()「所有处理」自动获得进度，不需要逐个改调用点
数据层原生 ProgressBus（ThreadLocal + 60ms 节流）；MainActivity.taskProgress() 注入 window.__taskProgress(job,pct,msg)；Bridge.request 生命周期内 begin/end工具类不改方法签名即可上报真实百分比

不确定进度的处理

并非所有任务都能预知总量（例如流式 7z 解压、dex2jar 内部阶段、签名）。这些任务显示 不确定动画：填充条保持 34% 宽度、1.05s 循环平移，说明文字仍实时更新。任务结束后进度条直接关闭，不会出现「卡在 90% 不动」的假死观感。

原生节流：同线程 60ms 最多推送一次；百分比未变化且无新文案时不重复 evaluateJavascript，避免大目录复制时把主线程刷爆。
