需求与对照

用户对比同一个 org/apache/commons/net/bsd/package-info.class（取自项目内置的 commons-net-3.10.0.jar），给出 MT 管理器与 r11 的不同输出，要求解释并修改。

MT 管理器（目标）

package org/apache/commons/net/bsd;

synthetic interface package-info version 52:0
{
  SourceFile               "package-info.java";
} // end Class org/apache/commons/net/bsd/package-info

r11 原输出

package org.apache.commons.net.bsd;
interface abstract class synthetic version 52.0

该文件经 javap -v 确认为 ACC_INTERFACE | ACC_ABSTRACT | ACC_SYNTHETIC（0x1600）、major 52、0 字段 0 方法、仅 1 个 SourceFile 属性。它是 javac 为包声明生成的合成接口，属于典型的「空类」。

根因：只对齐了主体，没对齐类头语法

r10 仿写反汇编器时，重点对齐了 Method … / stack N locals N / 逐条指令 / Lxx: 跳转标签 / 常量池引用注释这部分主体，类头却用了一个自定简化模板：

// classview.js r11，376-389 行
var cls = info.thisClass, dot = cls.lastIndexOf('.');
// thisClass 已被 cpClassName() 把 '/' 换成 '.'
out.push('package ' + cls.slice(0, dot) + ';');
// flags 按位拆成 before / after 两组，中间写死 'class'
var head = before.join(' ') + 'class' + after.join(' ')
           + ' version ' + info.major + '.' + info.minor;
  • 把 class 写死，于是 ACC_INTERFACE 与 ACC_ABSTRACT 同时命中时输出 interface abstract class synthetic；
  • 没有简单类名占位，版本写成 52.0 而非 52:0；
  • JVM 内部名 / 被统一换成 .；
  • disassemble() 只渲染字段与方法，完全不渲染类属性——其实 parse() 早已把 sourceFile 解析出来（实测 parseBase64().sourceFile === "package-info.java"），只是没用；也没有 { } 与结尾注释。

普通 class 有几十上百行指令撑着，类头差异被淹没；package-info.class 是 0 字段 0 方法的空类，把这层差异全部暴露，因此看起来「完全不像」。这不是解析错误，两者读到的字节完全一致。

本问题纯属前端文本模板：Java 层对 classview.js / disassemble 零引用，DEX 转 JAR（dexToJar）与 JADX 反编译（dexCode）都不经过它，因此不影响反编译 APK 的能力（详见文末链路隔离）。
