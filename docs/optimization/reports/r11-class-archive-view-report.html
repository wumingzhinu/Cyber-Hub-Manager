需求与现象

用户对比两张截图后指出：「jar 里面的 .class 文件还是如一图所示，效果要改成二图对标 MT 管理器」。图一是 r9 的四标签「类信息查看器」表格（概览 / 字段 / 方法 / 字符串），图二是 MT 管理器同款的深色字节码反汇编代码视图。

关键在于：r10 已经把 .class 默认打开改成了反汇编编辑器，本地散装 .class 看起来正常，但从 JAR / ZIP / APK 归档里点开的 .class 仍稳定回到图一表格。这不是「没改」或「改错了」，而是覆盖安装后 WebView 缓存了旧组件。

根因：缓存里的旧 classview.js 触发了表格回退

r10 已改用 disassembleBase64()→ 覆盖安装（versionCode 恒为 55）→ WebView 复用 r9 版 vendor/classview.js→ 旧组件只有 parseBase64()→ dis = null→ return classInfoScreen(f)

r10 的 classScreen() 里留了一条防御性回退：

let cv = window.CyberClassView, dis = classDisasmOf(cv, b64);
if (!dis || !dis.valid) { return classInfoScreen(f); }   // r10：反汇编失败就退回四标签表格

由于 versionCode 一直是 55、签名证书也相同，用户是覆盖安装而非全新安装，WebView 的 HTTP 缓存里仍是 r9 时代的 vendor/classview.js：该版本有 parseBase64() 但没有 disassembleBase64()。于是 classDisasmOf() 返回 null，代码走回退分支；而旧组件的 parseBase64() 又能正常把 class 结构渲染成四标签表格，所以现象稳定、无报错、看起来完全像没改过。归档内条目走 fileData 通道且总是重新加载视图，因此比本地文件更容易复现。

结论：只要 classScreen() 还存在「反汇编失败 → 表格」这条路径，缓存、组件加载失败、损坏 class 中任一情况都可能把用户送回图一。必须让归档内 .class 无论组件新旧都恒进代码编辑器。

修复：删回退 + 三层兜底 + 缓存根治

层次措施作用
① 主路径classScreen() 删除 return classInfoScreen(f)；fileArgs(f) 对归档条目返回 {archive, entry, path}，经 DataEngine.fileData → resolve() → ArchiveTools.readEntry() 读出字节归档内 .class 一律进 renderEditor() 深色代码区，绝不回退表格
② 组件自愈新增 ensureClassView()：检测到 disassembleBase64 缺失时，以 ?v=UI_BUILD 重新注入 vendor/classview.js 并重试 classDisasmOf()覆盖安装后即便命中旧缓存，也能就地拉起 r11 版反汇编器
③ 内置反汇编新增 builtinClassDisasm(b64)：app.js 自包含 JVM 字节码反汇编器（常量池、字段、方法、Code 属性、205 个 opcode、跳转标签、引用注释），完全不依赖外部组件即便组件彻底加载不到，仍输出 MT 同款反汇编文本（真实 Sample.class 实测与主反汇编器一致：4 方法 / 89 指令 / 9 标签）
④ 最终兜底classStructText() / classBytesText()极端情况下（字节损坏等）也留在代码编辑器里显示结构或十六进制文本，不再跳出到表格页面
⑤ 缓存根治app.html 给 classview.js / app.js 加 ?v=r11；MainActivity.assetEpoch 4 → 5 触发 web.clearCache(true)；localAsset() 保持 LOAD_NO_CACHE + Cache-Control: no-store从源头清掉旧缓存，避免下一轮修复再次被旧资源吃掉

classInfoScreen() 仍保留，但降级为右上菜单的主动二级入口，不再是任何失败路径的自动落点。
