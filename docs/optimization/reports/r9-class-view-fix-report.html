一、症状

在文件管理器里进入 JAR / 压缩包（例如上一轮 r7「DEX 转 JAR」或 r8「JAR 归档浏览」的产物）后，点击其中的 .class 文件无法打开，界面报错：

二进制文件：无法作为文本打开，请在「打开方式」中选择十六进制查看器或其他应用

在「打开方式」对话框里选「编辑文本」时，异常被包成「无法完成」对话框弹出。归档内 / 本地的 .class 完全看不到任何内容——这正是 r8 报告明确标注「本轮未加入独立 .class 反编译」所留下的能力缺口。

二、根因：分类缺失 → 文本读取 → 二进制拦截

报错文案精确来自 DataEngine.read() 的二进制字节码扫描：FileOps.read(f, MAX_TEXT) 读回字节后，若前 2048 字节出现 0x00 就抛错。Java class 文件以魔数 CA FE BA BE 开头，其后全是版本号、常量池索引等二进制数据，必然命中。

openFile(f) → fileType(f)        // archiveExtensions / textExtensions / 专属列表都不含 class → 'file'
  → openText(fileArgs(f), f)      // 未知类型一律兜底当文本打开
  → rpc('read') → DataEngine.read() → FileOps.read(f, MAX_TEXT)
  → 前 2048 字节扫到 0x00 → IOException("二进制文件：无法作为文本打开…")

更糟的是 openWithBuiltinItems() 的「编辑文本」调用 openText(fileArgs(f)) 没有传 f，使 openText() 里 f && !f.dir && msg.includes('二进制文件') 的兜底失效，异常被 act() 捕获后弹成「无法完成」对话框，用户连「打开方式」都回不去。

关键：后端其实早就能拿到 .class 的字节。DataEngine 的 fileData action = ExtraTools.fileData(resolve(a))，返回 base64；resolve() 对归档内条目会先 readEntry() 解出临时副本。缺的只是「前端把 .class 当成一种可查看的类型」，而不是任何原生能力。

三、修复：内置 .class 类信息查看器

参考 MT 管理器查看 class 的能力，新增一个离线结构化查看器，点击即能看到内容，而非落到错误页或只有十六进制。全部在 WebView 前端完成，Java 层零改动。
