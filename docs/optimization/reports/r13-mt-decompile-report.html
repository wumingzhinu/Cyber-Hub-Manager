本轮与 r12 的本质区别

r12 只对照了用户贴出的一段 MT 输出文本 + commons-net 样本 + javap -v，属于「照文本仿写」；用户随后明确要求「再次修改，要基于 MT 管理器反编译修改优化 r12」。r13 不再猜测，而是直接反编译 MT2.26.11.apk 安装包本体，从 APK 内的真实语法定义、dumper 明文格式串、属性常量与 opcode 表中提取权威规则，再系统性改造代码。

由此发现并纠正了一个 r12 及之前完全没暴露的问题：r10–r12 的指令助记符 aLoad_0 / aConst_null / iStore_1 是自创 camelCase 拼写，在 MT 全库检索命中数为 0；MT 用的是 Jasmin 标准小写 aload_0 / aconst_null / istore_1。这不是外观差异，而是「是否忠实于 MT 真实实现」的差异——只有反编译安装包本体才能查出来。

二、关键纠错：camelCase 助记符在 MT 全库零命中

// 全库检索（jasm.mtsx + 5 个 dex 字符串池 + 4,677 个 smali）
aLoad_0 / aConst_null / iStore_1  …  命中 0
aload_0 / aconst_null / istore_1 …  命中 7 + 完整 opcode 表长字符串

r10–r12 仿写 opcode 表时按「驼峰」命名生成助记符（aLoad_0），MT 实际输出的是 Jasmin 标准小写（aload_0）。package-info.class 是空类、没有方法体，因此这个错误在之前几轮的用户截图中完全不可见；一旦打开带方法体的 .class，整页指令就与 MT 不同。

两处独立实现的 opcode 表（classview.js 与 app.js 内置反汇编器）同时改为标准小写，并在自检中对「剥离注释后的代码」做 camelCase 零残留断言，防止回归。

五、三处反汇编实现的一致性
