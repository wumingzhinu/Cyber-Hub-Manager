一、症状

在文件管理器中对 DEX 文件执行「DEX 转 JAR」时无法完成，提示 cant find zipfs support。该功能入口为 app.js 的 dexToJar() → DataEngine 的 dexToJar action → DexEngine.toJar()。

报错与 DEX 内容无关：只要是转 JAR 就必失败，而 DEX 转 Smali、DEX 编辑、JADX 反编译都正常 —— 说明问题集中在「生成 JAR 压缩包」这一步。

二、根因（反编译依赖库确认）

项目内置 app/libs/dex-translator-v2.4.jar（dex2jar 2.4）。DexEngine.toJar() 原实现：

File part = new File(work, input.getName() + ".jar");   // 尚不存在的文件路径
Dex2jar.from(input).skipDebug(false).to(part.toPath());

反编译 com.googlecode.d2j.dex.Dex2jar 发现：

  • 该类只有 to(Path) 一个输出方法，没有 to(File) / to(OutputStream) 重载。
  • 常量池里有字符串常量 #63 = "cant find zipfs support"。
  • to(Path) 开头判断 Files.exists(path) && Files.isDirectory(path)：命中走 doTranslate(path)；否则调用私有 createZip(Path)。
  • createZip() 遍历 FileSystemProvider.installedProviders() 找 scheme="jar" 的 provider；找不到就抛 IOException("cant find zipfs support")。

Android 运行时只提供 file / jrt provider，没有 JDK 的 jdk.zipfs 模块，因此遍历必然落空。这是 dex2jar 面向桌面 JDK 的假设，在 Android 上不成立。

三、突破口：让 to(Path) 走目录分支

继续反编译内部类 Dex2jar$1$1.visitEnd()，确认目录分支只用这些 API 把 .class 写进目录：

Path target = dist.resolve(className + ".class");
if (!Files.exists(target.getParent())) Files.createDirectories(target.getParent());
Files.write(target, classBytes);          // Android API 26+ 全部支持

即：只要传入一个已存在的目录，to(Path) 就完全不调用 createZip()，也就不依赖 zipfs。转换结果是一棵按包名组织的 .class 目录树，再由我们自己按相对路径写进 ZipOutputStream 即可 —— 无需改动第三方库、无需往 APK 里塞 zipfs 实现。

五、对照实验（在无 zipfs 的 JVM 上复现并验证）

用 java --limit-modules java.base 启动，排除 jdk.zipfs，使 installedProviders() 只剩 file / jrt —— 这与 Android 的环境一致。对同一个真实 DEX 分别调用旧、新两条路径：

providers: file jrt
OLD_PATH(文件.jar) = FAIL -> cant find zipfs support
NEW_PATH(已存在目录) = OK

旧路径精确复现了真机报错，新路径正常完成 —— 直接证明根因判断与修复方案都成立。
