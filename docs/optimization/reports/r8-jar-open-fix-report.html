一、症状

在文件管理器中点击 JAR 文件（例如上一轮 r7「DEX 转 JAR」生成的产物）时无法打开，界面直接报错：

文件过大，无法执行此操作（上限 8 MB)

这不是「文件真的太大打不开」，而是打开方式走错了：JAR 是 ZIP 容器，本应像 ZIP / APK 一样进入双窗格压缩包浏览，却被当成普通文本读入编辑器，于是撞上文本编辑器的 8 MB 保护上限。

二、根因：前端分类链路

报错文案精确来自 FileOps.read(File, long)：

public static final long MAX_TEXT = 8L * 1024 * 1024;
public static byte[] read(File f, long limit) throws IOException {
    if (f.length() > limit)
        throw new IOException("文件过大，无法执行此操作（上限 " + limit / 1048576 + " MB)");
    ...
}

调用链一路回溯到点击动作：

openFile(f)                          // app.js
  └─ fileType(f)                     // archiveExtensions 不含 'jar' → 返回 'file'
       └─ return openText(...)       // 兜底分支：未知类型一律当文本打开
            └─ rpc('read')           // DataEngine.read()
                 └─ FileOps.read(f, FileOps.MAX_TEXT)   // 8 MB 上限

archiveExtensions 原有 zip / rar / 7z / tar / gz / … / iso，唯独漏了 Java 归档；fileType() 末尾的专属列表也只含 apk / apks / dex / xml / java / smali / arsc。因此 x.jar 落到 'file'，进入 openFile() 最后一行的文本兜底。

后端其实一直是好的：ArchiveTools.format() 对未知扩展名默认返回 "zip"，listEntries() 用 zip4j 列条目、readEntry() 提取条目，DataEngine.list() / resolve() 也都按归档路径分发。缺的只是前端把 JAR 归类为归档。

三、同一根因的两种表现

JAR 大小命中的检查用户看到的报错
< 8 MBDataEngine.read() 扫描前 2048 字节发现 0x00二进制文件：无法作为文本打开，请在「打开方式」中选择十六进制查看器或其他应用
> 8 MBFileOps.read() 的长度前置判断文件过大，无法执行此操作（上限 8 MB)

本次实测样本里，单 DEX 转出的 JAR 为 7,058,565 字节（会报「二进制文件」），3 DEX 合并转出的 JAR 为 23,597,013 字节（正是用户所见的 8 MB 报错）。两种症状同源，一次分类修复同时消除。

七、兼容边界与未改动项

  • 8 MB 文本上限本身不变：FileOps.MAX_TEXT 仍是 8L * 1024 * 1024。修复的是「JAR 不该走文本读取」，而不是放宽文本编辑器保护；显式用「编辑文本」打开超大文件仍会收到提示，但现在会给出可操作的出路。
  • 归档内 .class 条目：作为二进制文件，点击后会走原有的「二进制文件」引导，可在「打开方式」中选择十六进制查看器；本轮未加入独立 .class 反编译（那是另一项能力，需 Java 反编译器支持）。
  • versionCode 55、versionName 0.1.59、签名密钥、默认中文文案、13 项打开方式网格、长按菜单项数，以及 r4 / r5 / r6 / r7 的全部修复均保持不变。

八、使用说明

覆盖安装新 APK 后，直接点击任意 .jar / .war / .ear / .aar / .jmod：应进入双窗格压缩包浏览，可逐层展开包路径、查看 META-INF/MANIFEST.MF、解压或提取条目，不再出现「文件过大」提示。建议优先用 r7 生成的 20 MB 以上 JAR 复测，效果最明显。

若点击后仍看到旧报错，请确认已安装本包（编辑器信息栏或「关于 → 版本说明」应显示 r8），并从最近任务划掉应用后冷启动，避免 WebView 复用旧 app.js 缓存。
